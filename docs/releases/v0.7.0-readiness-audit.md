# PineAssure v0.7.0-rc.1 readiness audit

## Audit scope and evidence boundary

This audit records the repository state observed before implementing the
updated Repeatable Field Audit contract and the release-candidate closure
performed on 2026-08-05. The initial reference was branch
`feature/repeatable-field-audits-store-v0.7.0` at commit
`4dc574c708956506c3324a8443c543aa9e580202`.

The audit covers the module router, backend persistence, public schemas,
Angular frontend, tests, CI, package verification, dependency evidence,
benchmarks, and release documentation. It does not claim physical WiFi
Pineapple Mark VII validation.

The checklist is intentionally fail-closed: a gate is complete only when the
implementation and its verification evidence exist at the same final commit.

## Contract decisions

- PineAssure is the display brand; `PineAI` remains the technical module,
  package, state-directory, and CLI compatibility identity.
- Multiple draft runs are allowed. Only one run may be `in_progress` per
  assessment.
- Closing the browser does not change state. Returning to an `in_progress` run
  is the resume mechanism; v0.7 has no persisted paused state.
- Resolution accepts operator-selected saved Recon JSON, processes one
  observation at a time, and never starts or stops a radio.
- `local_full` and `share_safe` are the v0.7 AuditRun privacy profiles.
- A release candidate may be published with hardware validation pending. A
  final stable tag requires exact-asset Mark VII evidence.

## Release-candidate closure evidence (2026-08-05)

Commit `8985591` removes the two unsupported Mark VII UMD externals that were
found after the earlier device exercise. The unused RxJS state stream and CDK
scrolling module were removed, the two virtual-scroll lists now use bounded
`div` containers with stable `trackBy` functions, and package staging and
archive verification fail with `unsupported_umd_dependency` for either root
or subpath imports of `rxjs` and `@angular/cdk/scrolling`.

The clean workstation gate at that source commit produced the following
results before this documentation-only checkpoint:

- 290 Python tests passed in WSL and Windows Python 3.8.20 with the pinned
  schema dependencies; Windows had 14 intentional POSIX/socket-only skips;
- 52 of 52 Angular tests passed under Node 16.20.2 and ChromeHeadlessCI;
- coverage was 50.57% statements, 36.53% branches, 58.68% functions, and
  50.36% lines;
- Angular lint and the production build passed, and the real production UMD
  contains neither forbidden external;
- the exact package verifier, isolated imports, passive offline smoke,
  deterministic SBOM generation, secret scan, docs/schema checks, Ruff,
  compileall, and benchmark smoke passed;
- Angular e2e is unavailable because `angular.json` defines no e2e target. It
  is not reported as passed.

The Windows matrix also exposed a transient antivirus/sync-provider directory
lock while atomically publishing a restore-staging tree. Commit `b3bc144`
adds a bounded retry around the same `os.replace` operation without falling
back to a non-atomic write. The regression and all 14 backup tests pass on
Windows and WSL, and both complete 290-test matrices are green.

The local archive generated before this documentation commit is diagnostic
evidence only. Exact package, checksum, SBOM, test, coverage, and dependency
evidence for publication must come from the green branch, merged `main`, and
tag CI runs. Their release files must compare byte-for-byte before the
pre-release is published.

Removing virtualization means the bounded list containers may render the
current backend maxima of 1,000 access points or 500 findings. Correctness is
covered, but that worst-case UI load has not been benchmarked on Mark VII and
is recorded as an RC limitation.

## Superseded hardware evidence

The 2026-08-02 device runs remain useful historical backend, package,
resource, recovery, and rollback evidence. They do not validate the new
frontend artifact: the old bundle still externalized `rxjs` and
`@angular/cdk/scrolling`, and serving it byte-identically did not prove that
the authenticated Hak5 application could initialize it. All exact-RC hardware
checkboxes above are therefore reset to pending.

The automated release verdict may become **GO for v0.7.0-rc.1 with hardware
validation pending** only after PR, merged-main, tag, and byte-identity gates
pass. Stable `v0.7.0` and Hak5 upstream submission remain **NO-GO** until the
published RC bytes pass the physical procedure.
